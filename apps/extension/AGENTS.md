# AGENTS.md

## App Boundary

- This is the Chrome MV3 extension app, built by Vite + `@crxjs/vite-plugin` from `manifest.config.ts`.
- Popup entry is `src/popup.tsx`; routes are generated by `vite-plugin-pages` from `src/pages` and consumed through `~react-pages` in `src/App.tsx`.
- Background service worker entry is `src/background/index.ts`.
- Content scripts for element copying, translation, video sniffing, recording, and network monitoring are registered separately in `manifest.config.ts`.
- `src/content-script/index.ts` connects the top-level page to the development HMR/debug client; keep it independent of feature handlers.
- Home page feature entry points stay card-based. Cookie editor opens its webpage panel; other detailed editing workflows use modal dialogs.

## MV3 Gotchas

- `manifest.config.ts` scans `src/content-script` into `web_accessible_resources`. For separately injected modules, use CRXJS `?script` loaders with `chrome.scripting.executeScript({ files })` so their dependencies are bundled and exposed; functions passed through `func` must be self-contained.
- Default extension options live in `src/store/options.ts` (`DEFAULT_OPTIONS`); option types live in `src/types.ts`.
- `chrome.storage.local` is the source of persisted options; `src/store/options.ts` mirrors it into Jotai.

## Popup And Options UI

- Popup and options pages use Preact with `preact/compat` and `@preact/preset-vite`, plus Base UI, Jotai, React Router, Tailwind v4, and `normalize.css`.
- Base UI, `react-router-dom`, and `react-hook-form` rely on `preact/compat` compatibility.
- `pnpm install` reports missing React peer warnings for those libraries; this is expected because React runtime is intentionally not installed.
- Tailwind v4 is wired through `@tailwindcss/vite`; `src/index.css` imports theme/utilities only, so Tailwind preflight stays disabled.

## Content UI

- Applies to all webpage-injected UI, including recording and network panels, translation cards, video buttons, and copy feedback. Read `../../docs/adr/0001-content-ui-vanjs-inline-styles.md` before changing its architecture or isolation policy.
- Use `vanjs-core` and native inline `style`. Keep Preact, Tailwind, and popup/options global styles out of content UI dependencies.
- Compose business UI from shared atomic components in `src/content-ui/`; use its fixed light theme for colors, typography, spacing, radii, and layers. Keep business content, layout, Chrome messaging, and configuration subscriptions in feature modules.
- Components are functions returning native DOM nodes, composed through props and children. Drive interactive styles with events and VanJS state.
- Mount directly into webpage DOM. Do not introduce Shadow DOM, iframe isolation, or `!important`; host styles overriding content UI are an accepted boundary.
- Use the shared mounting and scope helpers. Feature views expose `dispose()`; unmounting must remove DOM and release global listeners, subscriptions, timers, and other owned resources. Repeated toggles must not accumulate mounts or listeners.
- Update locally and reuse stable nodes to preserve focus, selection, scroll positions, and panel dimensions. Preserve existing business behavior, message protocols, and frame-specific responsibilities.
- Movable, resizable panels (Cookie editor, network monitor, step recorder) use `src/content-ui/panel-geometry.ts` to load geometry before mounting, share title-bar dragging, and save only after a drag changes position or native resize changes inline dimensions and actual size. Each panel has an independent `chrome.storage.local` key (`contentUiPanelLayouts.<panel-key>`) shared across sites and tabs; restoration and dragging use the same 8px viewport margin and per-panel minimum sizes, reduced when the viewport is smaller.- Mark every UI root with `data-chrome-ninja-ui` and exclude its clicks, input, and scroll from recording via `isContentUIEvent`. Handle propagation only where the feature needs it.
- Reuse the shared Toast for both normal copy feedback and the independently injected failure entry. Browser-restricted pages retain best-effort logging; this path does not bypass injection restrictions.

## Cookie Editor

- `src/cookie-editor/background.ts` owns the `cookie-editor` message commands, Cookie observation, and persisted disable rules. Read the Cookie editor section in `README.md` for removal attribution and recovery boundaries.
- The Popup component only opens the editor. `src/cookie-editor/content.ts` is injected with a CRXJS `?script` loader and acknowledges mounting; `panel.ts` owns webpage drafts and subscriptions.
- Scope comes from the sender tab (top frame), its Cookie store, and `chrome.cookies.getPartitionKey`. Identity includes name, Domain, Path, store, and both partition key fields. Expired writes remove an exact identity; URL/name removal is insufficient.
- Tests exercise messages/events in `tests/cookie-editor-background.test.ts`, webpage behavior in `tests/cookie-editor-panel.test.ts`, and the Popup entry in `tests/cookie-editor-entry.test.tsx`.

## Browser presets

- `src/browser-preset/background.ts` owns the `browser-preset` message commands (`list`, `create`, `update`, `delete`, `apply`, `simulate-exit`, `status`) over the dedicated `browserPresets` key in `chrome.storage.local`; presets stay separate from `options`.
- Records are `BrowserPreset` from `src/browser-preset/types.ts`: a stable `id`, a unique `name`, a `userAgent` value reused from `USER_AGENT_OPTIONS` (`default` means no UA override), and a `viewport` of width, height, device scale factor, and `mobile`.
- `apply` resolves the target tab from the sender (top frame; extension pages use the active tab), then runs `chrome.debugger.attach` → `Emulation.setDeviceMetricsOverride` → `Emulation.setUserAgentOverride` when the preset's UA is not `default` → `chrome.tabs.reload`, awaiting every call before the reload. Device metrics stay scoped to that tab across reloads, in-page navigation, and SPA route changes; no `webNavigation` listener re-issues commands and new tabs are untouched.
- Applying a second preset to a tab that is already simulating reuses the existing debugger session: it skips `attach`, re-sends the emulation overrides, and reloads. It never detaches and re-attaches, so the browser's debug banner is not shown again. A failed reuse keeps the existing session mapped so 退出模拟 can still detach it.
- The UA override always sends `userAgent`, `platform`, and the full `userAgentMetadata` together; Safari-class identities omit `userAgentMetadata` entirely, which is what suppresses every `sec-ch-ua-*` header. A `default` preset sends no UA override at all. See `docs/adr/0003-browser-preset-via-cdp.md`.
- While a tab is simulated with a concrete UA, the global `UserAgent` DNR rule is suspended so the two cannot emit contradictory headers; a `default` preset never touches it. `src/user-agent/index.ts` owns this: `suspendUserAgentRule`/`resumeUserAgentRule` ref-count the simulated tabs, and `applyUserAgentRule` keeps recording the user's latest choice without writing the rule while suspended, so the existing `storage.onChanged` re-sync cannot undo the suspension and the user's own change is not lost. `resumeUserAgentRule` restores that latest choice after the last tab exits.
- `status` returns the same target tab plus `unavailableReason`, derived from `pageUnavailableReason()` in `src/cookie-editor/types.ts` and an attached `chrome.debugger` target. `apply` reuses that reasoning and refuses before attaching. The page disables the apply button and shows the reason while it is non-empty, so restriction and DevTools takeover are handled before the click.
- `appliedByTab` is a module-level `Map<tabId, { presetId, groupId }>` in the background; it is memory only and clears on extension restart. `ownedGroupIds` is a sibling `Set<number>` of groups this extension created.
- Applying a preset also moves the tab into a tab group titled `[ninja] <preset name>`, created with `chrome.tabs.group` and titled with `chrome.tabGroups.update`. `apply` joins an existing owned group whose current title matches the preset, and falls back to creating a new group when the stored group is gone or the join fails; the new id is recorded in `ownedGroupIds`. Reuse is resolved from owned ids only, never from group titles, so a user-made group with the same name is never claimed. The `tabGroups` permission exists solely for `chrome.tabGroups.update`/`get`.
- `endSession(tabId)` is the single exit path, shared by the `chrome.tabs.onUpdated` `groupId` handler and the `simulate-exit` command: it returns any borrowed global-rule suspension, detaches the debugger (Chromium drops every emulation override on detach), ungroups the tab, and reloads. Chrome closes a group once it is empty, and a stale id is dropped from `ownedGroupIds` when the next apply cannot read it. `simulate-exit` does nothing on a tab that is not simulating, so it never reloads a page it has no overrides on.
- A `groupId` change away from the recorded group is treated as the user exiting the simulation, so dragging the tab out of its `[ninja]` group runs the same exit as the button.
- When the tab already belongs to a group outside `ownedGroupIds`, `apply` returns `needsGroupMoveConfirmation` without attaching anything; the resend with `confirmGroupMove: true` lets `chrome.tabs.group` move the tab out of the user's group and into the preset group.
- `status` also returns the target tab's `presetId` (absent when not simulating). Both the preset page and the Home card read it to show 正在模拟「预设名」 or 当前没有模拟, and both expose 退出模拟; the Home card places that button next to, not inside, its navigation button.
- `chrome.debugger.onDetach` cannot say why the session ended, so attribution looks the tab up. A tab that still exists was preempted by DevTools (or cancelled), so `attributeDetach` records a one-shot notice and runs `endSession`; a tab that no longer exists just drops its `appliedByTab` entry with no reload and no notice. A detach for a tab with no entry is ignored, so the extension's own `detach` inside `endSession` does not recurse.
- Notices live in the module-level `notices` map and are handed out by `status` as `notice`, then cleared on read so the page does not show the same message twice. `BrowserPresets.tsx` seeds its existing status line from it.
- `src/browser-preset/validation.ts` is the single source of name uniqueness (trimmed, case-insensitive), the 200–4000 width/height bounds, and the 1–4 device scale factor. The background and the page share it, so the first error text matches in both.
- `src/browser-preset/identity.ts` binds each built-in UA value to its `UserAgentIdentity`: the UA string comes from `USER_AGENT_OPTIONS`, joined by `navigator.platform` and a complete `userAgentMetadata`. No metadata field is left to a host fallback; Android identities send `bitness: ""` and Safari-class identities carry no metadata at all, so no `sec-ch-ua-*` headers are emitted. All versions stay on `Chrome/127`.
- `mobileConflictOf` compares the identity's `metadata.mobile` with the preset's `viewport.mobile`. A disagreeing pair makes `create`/`update` return `needsConfirmation` plus the `MobileConflict` detail (`sec-ch-ua-mobile` value, layout treatment) and writes nothing; the page shows a confirmation dialog whose 确认风险 resends the same draft with `confirmConflict: true`, and whose 取消 keeps the form untouched. Stored values are never corrected silently.
- `src/browser-preset/devices.ts` holds the device tiers. They only fill the viewport fields and are never stored.
- `/browser-presets` renders `src/pages/BrowserPresets.tsx` from the Home card in both Popup and Options. First-time copy explains that applying a preset needs the debugger permission. The device scale factor input uses `step="any"` because tiers such as the Pixel 8 send 2.625, which a fixed step would reject before the form submits.
- Tests exercise the protocol in `tests/browser-preset-background.test.ts`, the identity packages in `tests/browser-preset-identity.test.ts`, the page in `tests/browser-presets-page.test.tsx`, and the Home card in `tests/home-browser-preset-entry.test.tsx`.

## Dev Debugging/Popup Debugging

- Open `chrome-extension://<id>/index.html` in a normal browser tab — that page is the extension popup, so it can be debugged like any web page (`<id>` is the extension ID from `chrome://extensions`).
